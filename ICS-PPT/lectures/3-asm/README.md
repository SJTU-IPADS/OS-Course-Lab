float dot_product(const float *w, const float *x, int n) {
    float sum = 0.0f;
    for (int i = 0; i < n; i++) {
        sum += w[i] * x[i];  // <-- 整章的灵魂：硬件怎么执行这行代码？

# 第二章教学大纲：一行大模型代码的硬件之旅

### 序幕：问题的提出

* 情境：在第一章中，我们已经在内存里放好了输入 Token 的向量 x，以及从磁盘 GGUF 文件中加载出来的模型权重 w。
* 任务：Transformer 想要预测下一个词，第一步就是要算 w 和 x 的内积。我们写出了上面的 C 语言函数 dot_product。
* 悬念：现代 CPU 根本不懂什么是 for，什么是 w[i]，什么是浮点数乘法。硅片上只有数以亿计的晶体管和电路开关，它是怎么把这一行代码执行完并算出结果的？

---

### 第一部分：拆解单个计算——算力只能在“工作台”上发生

> 核心任务：先不管循环，就看最核心的这一瞬间：w[0] * x[0] 是怎么被 CPU 算出来的？

* 观察：数据存放在内存仓库中，但运算器（ALU）无法直接跨越总线对多级内存的数据就地计算。
* 冯·诺依曼架构的本质：CPU 算力与内存的分离。
* 方案【通用寄存器 / 浮点寄存器】：CPU 内部极速但极其有限的“案头工作台”（%xmm0, %rax...）。为什么寄存器只有十几个，而不能有几万个？

* 问题：CPU 怎么知道 w[i] 在内存的哪个角落？
* 观察：数组指针与步长，w[i] 本质是首地址加偏移。
* 方案【寻址模式（Addressing Modes）】：硬件如何用一条指令完成 Base + Index * Scale + Displacement 计算？让学生看到硬件层面为数组访问专门设计的电路支持。

* 问题：如何把内存里的数据抓到工作台上？
* 方案【数据搬运指令（Load: movss）】：把 w[i] 读入寄存器，把 x[i] 读入寄存器。

* 执行计算：
* 方案【算术指令（mulss / addss）】：ALU 接收电信号，寄存器内的比特流翻转，完成一次乘法与累加。

* 🎯 第一部分落地物：学生亲手写出第一段汇编微片段——加载一个数、加载另一个数、相乘、累加。

---

### 第二部分：让机器自己转起来——循环控制的本质

> 核心任务：单个乘法走通了，但内积有 n=4096 维，C 语言里的 for (int i = 0; ...) 在硬件里根本不存在，硬件如何自动循环 4096 次并停下来？

* 观察：CPU 的默认行为是沿着指令序列单向取指执行，程序计数器（PC / %rip）只懂一条一条指令往下推移。
* 问题：怎么让执行流“倒流”回去？
* 方案【无条件跳转（jmp）】：修改 PC 寄存器的值，让执行流跳回第一部分的计算片段。

* 问题：一直倒流就会导致死循环，硬件如何知道“4096 次已经满了”？
* 观察：计算机没有直觉，硬件靠的是“运算的副作用”。
* 方案【条件码 / 状态标志（Flags: ZF, SF）】：每次循环 i++，CPU 用一条减法或比对指令（cmp），计算 i - 4096。硬件不关心结果存哪，只在标志寄存器里立一个电平信号（结果是否为 0？是否为负？）。

* 问题：硬件如何根据这些状态信号改变执行路径？
* 方案【条件跳转（jge / jne）】：逻辑分支的物理实现。

* 🎯 第二部分落地物：把第一部分和第二部分拼接起来，学生得到了一个完整的、带循环控制的 dot_product 汇编片段。通过单步调试追踪一次完整的循环，看 PC 怎么跳、寄存器怎么变、标志位怎么翻转。

### 第三部分：从代码组织到过程调用——函数的硬件实现机制

> 核心任务：在正常的软件工程实践中，为了代码的模块化、可读性与复用，我们自然会把内积逻辑封装为一个独立的函数。硬件是如何为这种通用编码范式提供底层支持的？

* 观察：函数调用是现代编程语言中最核心、最固定的控制转移范式，它包含“跳过去执行”与“执行完返回原处继续”两个紧密相连的动作。
* 问题：如果只用普通的跳转指令（jmp）跳过去，硬件在执行完毕后并不知道该跳回哪里。
* 方案【指令集针对函数调用的专门设计】：
* 复杂指令集（x86-64）的思路：因为函数调用高度固定且频繁，x86 设计了专门的 call 与 ret 复合指令，自动在控制流跳转的同时完成返回地址的入栈与弹栈。
* 精简指令集（ARM64）的对比：遵循“尽可能复用基础指令、简化单条指令逻辑”的设计哲学，ARM64 没有类似 x86 的复合入栈指令，而是直接复用分支指令，通过 Branch with Link（bl）把返回地址存入专门的链接寄存器（LR / X30），返回时再使用 br X30 跳回。通过对比让学生深刻体会 CISC 与 RISC 在软硬件接口设计上的权衡。

* 问题：dot_product 作为一个独立的函数，输入参数（w, x, n）从哪里送进去？计算完成的浮点累加和又怎么交给调用者？
* 方案【应用二进制接口（ABI）与寄存器约定】：统一的接口契约。明确规定前几个整型/指针参数按序进入 %rdi、%rsi、%rdx，浮点运算结果固定放置在 %xmm0 中供调用方读取。

* 观察：大模型包含复杂而深层的函数嵌套调用，但可用的寄存器资源极其有限。
* 问题：当函数层层调用时，如何保证大家的局部数据不会在有限的寄存器里互相踩踏？
* 方案【运行时栈（Stack）与调用规约】：
* 栈指针 %rsp 的自动伸缩机制与函数栈帧的建立与释放。
* 调用者保存（Caller-saved）与被调用者保存（Callee-saved）的职责划分，从机制上保障多模块协作的内存安全。

* 🎯 第三部分落地物：将第二部分的代码封装为一个标准的函数，用外部 C 语言程序完成调用，观察 call、ret、栈指针伸缩及寄存器恢复的完整执行流程。

### 第四部分：性能瓶颈与现代突围——从标量计算到向量与并发

> 核心任务：大模型生成一个词，要算成千上万次 dot_product。算一下时间，硬件被卡在哪里了？

* 观察与算账：算力的结构性浪费
* 剖析第二部分手写的标量循环：算一次 w[i] * x[i] 只需要 1 次乘法和 1 次加法，但为了维持循环，硬件还要执行 add (i++)、cmp、jne、算寻址偏移……
* 结论：CPU 忙了半天，超过 70% 的机器指令居然是在维护循环计数器和跳转，根本没在算模型！

* 方案一：CPU 内部的向量化（SIMD 革命）
* 观察：现代 CPU 的内部总线和寄存器位宽远不止 32 位，单次只搬运和计算一个 32 位浮点数是对总线带宽和运算阵列的巨大浪费。
* 方案【向量寄存器（YMM 256-bit）】：一口气把 8 个浮点数（8 个权重）装进一个宽寄存器。
* 方案【向量融合乘加（FMA: vfmadd231ps）】：一条指令，同时完成 8 组数据的乘法和累加。
* 重构与对比：用一条 SIMD 指令替换掉刚才手写的多条标量指令，循环次数从 4096 次骤降到 512 次，无用的跳转与控制开销被大幅稀释。

* 方案二：面向大规模并行的视野拓展（从 SIMD 到 SIMT 与 GPU 雏形）
* 观察：CPU 的 AVX 即使做到了 256 位甚至 512 位，本质上依然是一个 CPU 核心在单线程地串行指挥指令流。面对庞大的大模型矩阵，CPU 即使拉满向量化依然存在算力瓶颈。
* 方案初探【SIMT（单指令多线程）与 GPU 硬件理念】：
* SIMD 类似由一个主控工人（CPU 单核）操作一把宽铲子，一口气铲起 8 份数据。
* SIMT 则是搭建几千个轻量级的小计算单元（GPU 核心），所有单元并发执行同一条指令逻辑，每个线程只独立负责计算对应位置的一组标量乘加。
* 概念铺垫：由于 SIMT 深度依赖多线程并发、线程束调度以及异构内存体系，本章不做过多微架构展开，但建立起“SIMD 是单核内部拓宽数据通路，SIMT 是多计算单元的大规模硬件并发”的宏观认知，为后续并行计算章节做好理论铺垫。

* 🎯 第四部分落地：
* 回到终端：在机器上打下 ollama run，给学生展示输出日志中的 CPU 架构支持输出：
llama_init_from_file: CPU features = AVX2, FMA
* 这一刻学生完全顿悟：这行日志不是一串无聊的英文缩写，它代表着这台机器正在用第四部分讲的向量电路，拯救前面几部分中慢如蜗牛的标量计算；同时也理解了为什么在大模型推理部署中，系统会首选将其卸载到 GPU 运行。
